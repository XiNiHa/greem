# Map: greem core

Label: wayfinder:map
Tracker: local-markdown (`.scratch/greem-core/`)

## Destination

Lock greem's core design and prove it with a walking skeleton in-repo: SDL → `build.rs` codegen → set-based (breadth-first) async executor → one query end-to-end, plus one `@defer` and one `@stream` query delivered incrementally, with a spec that points at the skeleton. Core decisions must leave room for what lands later (the `onError` wire attribute, subscriptions, federation, persisted queries, framework adapters); the map ends when the core is decided and the skeleton runs, not when those ship. (Incremental delivery moved into scope on 2026-09-26 by the @defer/@stream ticket.)

## Notes

- Domain: async Rust GraphQL server framework, schema-first, Tonic-style codegen. Core bet: a depth-first trait encoding (per-field marker traits the user implements `Resolver<F>` for; generated per-type completion impls bound on them) carries over to breadth-first.
- Source of the execution model: Shopify, "Faster breadth-first GraphQL execution" (Cardinal). Summary of what matters: resolve each field once per generation across the whole parent set; scopes hold index-aligned `objects`/`results`; lists flatten into the child scope; abstract scopes built lazily after the parent resolves; errors inlined, null-propagation done in a final depth pass; planning is a bottom-up "lookbehind" pass. Article is silent on async, `@defer`/`@stream`, and non-null semantics — those are greem's design work.
- Skills every session consults: `grilling` + `domain-modeling` for grilling tickets; `prototype` for prototype tickets; `research` for research tickets. Glossary lives in `CONTEXT.md`; challenge terms freely.
- Standing decisions from charting (not tickets; do not re-litigate):
  - Public, general-purpose framework; spec-compliant and ergonomic, but map tickets spend on the execution/codegen core.
  - Set-based resolution is the executor's only primitive; per-object resolvers are codegen sugar that desugars to it.
  - Per-field trait impl is the codegen primitive (one marker type per field, `impl Resolver<Query__user> for …`); `#[greem::object]`-style per-type sugar layers on top and is fully opt-out-able; distributed `impl`s are a requirement. Missing resolvers are compile errors at the schema boundary.
  - GraphQL return types are expressed as trait bounds on the user's output type (provisional trait `Outputs<Ty>`), not as wrapper types.
  - No user-maintained Rust↔GraphQL type mapping; the user's types are inferred through trait bounds.
  - Response is a custom index-aligned result arena, serialized once at the end.
  - Null propagation is post-hoc (final pass over the arena); `onError` HALT = stop enqueuing generations.
  - Generation barrier: all fields of all scopes in a generation run concurrently, next generation starts when all finish.
  - Executor is runtime-agnostic: `Send` futures, `join`, no spawning; tokio only in adapters/examples.
  - Reuse an existing parser/validator crate for v0.
  - Lookbehind planning is in the skeleton, not deferred.
  - Compliance = hand-written spec-algorithm tests + a naive depth-first reference executor with property-based BFS≡DFS equivalence.
  - Codegen is Tonic-styled: `greem-build` from `build.rs`, output in `OUT_DIR`, `include!`d.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [Which parser/validator crate does greem reuse?](issues/01-parser-crate-survey.md): apollo-compiler 1.33.x for both build.rs and runtime — the only candidate with spec-complete schema + executable validation against a pre-built `Valid<Schema>`, plus introspection execution and variable coercion; cost is ~81 crates / 8s cold debug build; pin 1.x and keep apollo types out of greem's public API ahead of the 2.0 rename churn. Its `resolvers::Execution` DFS executor is a candidate oracle for the BFS≡DFS tests. Runner-up: cynic-parser with greem owning validation.
- [What exactly is the current onError / error-behavior RFC?](issues/02-onerror-rfc-state.md): unmerged RFC 1 (graphql-spec #1163); top-level request attribute `onError` ∈ `NULL | PROPAGATE | HALT`, default forever `PROPAGATE`; error always appended first, then NULL nulls the position, PROPAGATE bubbles, HALT aborts the root selection set with `data: null` and exactly one error; silent on mutations and incremental delivery (HALT intended per incremental result); adds contested `pathNonNull` per error. Only Apollo Kotlin ships it; graphql-js has only `@experimental_disableErrorPropagation`.
- [What is the current incremental delivery (@defer/@stream) spec shape?](issues/03-incremental-delivery-spec-state.md): graphql-spec #1110 (RFC2, "June 2023" no-duplication format), landing in slices on `incremental-integration`; `@stream` execution text does not exist yet. Response: initial `data`+`pending`+`hasNext`, then `incremental` entries (`{id, items}` or `{id, subPath?, data, errors?}`) and `completed {id, errors?}`; fields never duplicated; a deferred fragment ships whole; a non-null error bubbling to the fragment/list boundary suppresses the entry into `completed.errors` — the delivered parent is never rewritten. Nulled initial positions drop incremental work beneath them. Only the outermost list streams; servers may ignore any directive but must send ≥ `initialCount` items. Transport spec is stale/non-normative (multipart/mixed). Interaction with `onError` undefined. graphql-js 17 is the reference implementation.
- [How do Cardinal and Grafast do bottom-up (lookbehind) planning concretely?](issues/04-lookbehind-planning-in-practice.md): Cardinal's pass is literally reverse-construction-order `plan(field, ctx)` once per root scope before any resolve; primitives are `preload(loader, args, keys)`, `on_preload {}`, a freeform `attributes` bag, and `planning_root` for navigating up; abstract positions re-run build+plan per concrete bucket after the parent resolves, with ancestors sealed. Delivery is untyped (`.then` into `attributes`) and must become typed, index-aligned slots in Rust. graphql-ruby's OSS descendant dropped planning entirely for `resolve_batch` + Dataloader; Grafast plans per-operation (cached, all concrete types up front) and its transferable bits are the positional `ExecutionDetails` shape and `deduplicate`/`deduplicatedWith`.
- [What does a user write for one field, and what does codegen generate around it?](issues/05-resolver-contract-and-codegen-surface.md): per-field typed Resolver primitive, borrowed outputs, index-aligned vectors, typed Context/Args, opt-out-able per-object sugar, exact GraphQL names and root-type schema boundary. Adapter placement and lifetime details are superseded by the Outputs prototype resolution below.
- [How are interfaces and unions represented on the Rust side without a type mapping?](issues/06-abstract-types-without-type-mapping.md): generated tag-side Completes impls with one Outputs bridge; compositional As/Either wrappers and sub-interface delegation; interface fields use concrete implementer markers. The Outputs prototype below revises error delegation and repeated-arm batching.
- [What are the execution tree, a scope, a generation, and the result arena?](issues/08-execution-tree-scopes-generations-arena.md): data-free request tree, owned per-(node, type) Plans, columnar result arena with shape/parent links and lazy error paths, generation barriers and serial mutation roots. The Outputs prototype below supersedes the original flat-loop/bump ownership and returned borrowing response.
- [Does the Outputs<Ty> trait encoding survive breadth-first execution?](issues/07-outputs-encoding-prototype.md): yes, with explicit per-field sugar, split slice/object lifetimes, a reserved parent-error hook, partition-arm scope identity, safe retained generation frames and callback-based borrowed serialization; cross-crate integrated execution and cancellation pass. Stable lazy Plan storage and depth policy are newly ticketed.
- [How does post-hoc null propagation and onError work over the arena?](issues/09-nullability-and-onerror-semantics.md): type-level nullability means a non-null position nulls only via an execution error; final pass is an error-driven, order-independent, subtree-rooted upward walk over codegen-emitted shape descriptors that rewrites the nearest nullable ancestor to `Propagated(id)`; `errors` deterministic per scope in generation order, no sibling suppression; HALT = barrier flag, `data: null` + first error; mutations pass per root chain and stop per mode; skeleton ships `ErrorBehavior { Null, Propagate, Halt }`, only the wire attribute is deferred.
- [How do @defer and @stream map onto generations and the arena?](issues/10-incremental-delivery-in-generations.md): one generation loop with delivery-group-tagged scopes and a global barrier that also emits payloads; a deferred fragment is a separate scope over the same objects (identity gains a delivery group; Plans split by group); overlapping fragments follow the spec's usage-set rule; `Streamed<S>` wrapper for lazy lists, exact `initialCount`, item errors as execution errors; streams live in owned continuation scopes polled by a pump inside every generation's join (no spawning, Tokio-only rejected for its `'static` asymmetry); composite columns gain per-turn `tails`; deterministic ids at release, one update result per barrier; the null pass takes a boundary and fails the group instead of rewriting delivered data; HALT per group; response primitive becomes a per-payload sink; `IncrementalDelivery { Disabled, Enabled }` with `if` resolved at tree build; `multipart/mixed` gated on `Accept`; equivalence = fold-and-compare property plus graphql-js fixtures for failures. Incremental delivery is now in the skeleton.
- [What can a field say to its ancestors during planning, and what does the skeleton ship?](issues/11-planning-hooks.md): hints only in v0 (loaders stay fog); one synchronous post-order pass per request at tree build over every statically known abstract arm, so hints under an interface reach ancestors above it; two default methods on `Resolver` (`hints` declares accepted types at Plan build, `plan` writes), hints typed by the accepting field and addressed by type to the nearest acceptor; delivered via a per-invocation `Context<C>` view; hints may shape results, so the reference executor runs the identical pass; delivery groups visible to writers, making the incremental fold property conditional; every Plan entry exists at build, identity (node, partition leaf), which narrows ticket 16.
- [How does SDL become generated code, and how does the runtime get the schema?](issues/12-build-pipeline-and-crate-layout.md): `greem`/`greem-build`/`greem-macros` plus an unpublished `greem-reference`; `greem_build::compile` or `configure()` with `out_dir`, explicit rerun-if-changed, multi-file SDL, `scalar(name, Codec)`, `absent_aware`, hidden `reference_executor`; `OUT_DIR/greem.rs` via `greem::include_schema!()`; public tags/markers/inputs/enums/`Schema<C>`, everything executor-facing sealed in `__private`, nothing apollo-typed; embedded SDL parsed once in `build() -> Result` with a version-skew check, shaped for a later apollo-free construction model; introspection via apollo `partial_execute` as pre-resolved root leaves; owned `InputValue` with an `Enum` variant, apollo coerces variables and greem coerces arguments at Plan build, `Option<T>` with per-input-type `Maybe<T>` opt-in; one `Scalar` trait on the generated tag, hand-written or emitted for `Uuid`/`Json`/passthrough codecs; generated enums only; `Schema::parse -> Arc<Document>` then `execute_with`/`execute`/`execute_request` over an `Operation` handle, request failures as flagged payloads, `greem::http` serde types and multipart encoder; `#[greem::object(schema, type, context)]`; MSRV rolling stable-2.
- [How is the BFS executor shown spec-correct?](issues/13-compliance-harness.md): `greem-reference` is a naive DFS that builds `serde_json::Value` directly with spec-style bubbling and calls set-based resolvers with one-element sets; `greem-compliance` holds a property schema plus one area schema per ported graphql-js spec area (several schemas per crate via a `file_name` amendment to ticket 12), `proptest` over three shrinkable inputs (document, world, interleaving) under a single-threaded executor; equivalence = ordered `data` JSON plus an unordered multiset of full error objects, weaker for HALT; fold property gated by `prop_assume!` on failed groups; call-count property proves the breadth-first claim; determinism properties across runs and interleavings; hand-written expected JSON never from snapshots; cancellation via gate resolver and drop log; unpublished `greem-bench` with portable, language-neutral workloads and a criterion consumer measuring BFS against the reference to bytes, built to grow into cross-language comparison.
- [Abstract-type derive over a user enum](issues/15-abstract-type-derive.md): `#[derive(greem::Abstract)]` in `greem-macros` emits the sealed `Completes` impl directly through `greem::__private` (a public partition trait is either incoherent with the generated `As` impl or context-blind, per the coherence probe); one `#[greem(schema, type)]` attribute per target, variant name = member with `#[greem(as = "…")]` override, membership checked by a generated per-(abstract, member) witness including the `implements` chain; single-field tuple variants, generics forwarded, impl generic over `C`; variants are partition leaves in declaration order, repeated members stay separate scopes; `#[greem(reference_executor)]` opts into the reference impl; implemented after the skeleton.
- [How are eagerly built Plan entries stored and borrowed per request?](issues/16-lazy-plan-storage.md): a per-request Plan table frozen after planning, two parallel `PlanId`-indexed arrays (mutable headers with parent/child links and per-field hint slots; immutable Any-erased typed payloads with field sets by group and `Result<Args<F>, Error>`); one entry per (node, partition leaf) shared by every scope there, repeated arms duplicate; one recursive walk (enter: id, args, `hints`; exit: child link, `plan`); one checked downcast per scope at creation, `&'req` reborrowed as `&'obj Args<F>`; `Context<C>` view per field invocation, amending ticket 11; bad arguments are field errors that skip the subtree in the pass; `hint` panics on an unaccepted type, `try_hint` returns `Option`; walk depth handed to ticket 17.
- [What execution-depth limits bound retained generation frames?](issues/17-generation-depth-limits.md): frame depth was the generation count, which `@defer`, stream turns and mutation roots stretch past the tree; instead of a generation cap, chains: a nested frame run parks when done and retires after its last payload, stream turns are sibling chains under a stream driver and mutation roots siblings under a root driver, all stepped by a per-request barrier handle in lockstep, so depth equals the static execution depth (checked fail-fast at tree build, `@defer` and `@stream` +1, lists/fragments/aliases/partition +0, max over mutation roots), `Schema::max_depth` default 32 beside apollo's untouched parser and introspection limits, evidence at 2× default on a 2 MiB debug stack plus turn and root depth-independence tests; per-chain result storage becomes a skeleton requirement and amends ticket 10's single loop.

- [Does the skeleton run end-to-end?](issues/14-walking-skeleton.md): yes. `greem`, `greem-core`, `greem-build`, `greem-macros`, `greem-reference`, `greem-compliance` and `examples/axum` run SDL → codegen → breadth-first execution with one `@defer` and one `@stream` query over `multipart/mixed`; seven property-based BFS≡DFS/fold/determinism/call-count/depth checks hold at 5,000 cases, 22 hand-written spec cases and the ticket-17 depth/cancellation/panic/1,000-turn/1,000-root evidence pass on a 2 MiB debug stack; the spec is [docs/spec.md](../../docs/spec.md) and the generated module is the codegen reference. Deviations (`Context<'req, C>` borrows instead of a lifetime-free `Arc` view, `Completes::reference` instead of two support traits, stored object paths, scope quiescence, merged-`@stream` validation) are listed in the spec. The map's destination is reached.
- [Does a Streamed output survive retained generation frames?](issues/18-streamed-output-prototype.md): yes with inspectable owner/dependent frames (`self_cell`) preserving one structured borrowed payload across sibling chains; consuming internal completion moves streams into owned continuations while the public Resolver/Outputs contract survives; cross-crate streaming, Vec, nested defer, group-local failures and cancellation pass; depth-64 completion/cancellation/unwind, 1,000 streamed items and 1,000 serial mutation roots pass on a 2 MiB debug stack. Supersedes opaque async-frame storage and the literal FuturesUnordered ownership sketch; the walking skeleton is unblocked.

## Not yet specified

- Polling efficiency: every top-level poll traverses the non-quiescent scope tree and every barrier walks it for stream turns; a ready queue keyed by waker plus per-scope dirty flags is the obvious next step once a benchmark shows the cost (ticket 14).
- Dataloader / cross-field dedupe story: whether set-based resolution leaves an N+1 worth a per-request loader primitive (Cardinal-style preloads batched across scopes, and the cross-position dedupe ticket 08 pointed at ticket 11); the planning pass from ticket 11 is where it would register; decide after the skeleton shows real resolvers.
- Per-delivery-group hint split: an accepting field seeing which of its hints came from deferred or streamed subtrees, so the initial fetch need not pay for them; the group is already on the node (ticket 11), no data-model change.
- Barrier-less scheduling (child scope starts as soon as its parent field resolves) as a later experiment against the generation barrier.
- Mid-generation HALT cancellation: a cancelable generation join that drops remaining scope futures once a group's HALT flag is set; extension point fixed by ticket 09 (flag now per delivery group per ticket 10), worth an experiment once the skeleton has real latency to save.
- Early execution for incremental delivery: a flag that enqueues deferred scopes immediately instead of parking them until release; no data-model change (ticket 10).
- Stream batch capacity and back-pressure tuning: the pump's per-turn capacity (default 100) and how the sink's consumer slows the executor; decide with real adapters.
- SSE transport for incremental delivery (graphql-sse) as a second adapter option; the axum example ships `multipart/mixed` only.
- Request context construction: `Context<C>` and `ctx.app()` are decided (ticket 05) and the axum example simply constructs `C` in the handler per request; still open is whether an extractor layer exists and how connection state reaches it.
- Instrumentation/tracing hooks: once-per-field-selection tracers as the article describes; needs the scope model first.
- Cross-language benchmark harness: ticket 13 fixed the portable workload format and the in-process criterion baseline in `greem-bench`; still open is the HTTP-level harness that re-implements each workload's resolver contract in async-graphql, graphql-js and others, and how latency simulation is kept comparable across runtimes.
- Execution-tree caching across requests (precursor to persisted queries): ticket 08 fixed the key as document + the `@skip`/`@include` variables the tree consumed, and moved args out of the tree; what remains is cache ownership, eviction, and sharing the tree across requests (`Arc` vs per-request clone); the planning pass and Plan entries are per request (ticket 11) and are rebuilt on top of a cached tree; the `Arc<Document>` from `Schema::parse` (ticket 12) is the natural cache anchor.
- Apollo-free runtime: greem's own executable validator and introspection over a greem-owned schema model, at which point greem-build emits construction code for that model instead of embedding SDL text; ticket 12 kept the embedded item private so the swap is invisible to users. Decide only if apollo's weight or its 2.0 churn becomes a real cost.
- `Maybe<T>` by schema coordinate: `absent_aware` takes input object type names (ticket 12); single arguments (`Mutation.updateUser.name`) and a user-enum link at enum positions are additive follow-ups once a schema asks for them.

## Out of scope

Beyond this map's destination; expected to land as later efforts, not resumptions of this one.

- Client crate: never in greem.
- Subscriptions: different execution shape (event-driven, single root field); core must not foreclose, but no tickets here.
- Federation / subgraph support: entity resolution in the set-based model is a later effort.
- Persisted queries: the id/hash/store layer. Ticket 12 keeps the door open with `Schema::parse -> Arc<Document>` and a text-optional `Request`.
- Framework adapters beyond a single `axum` example in the skeleton.
- Full graphql-js fixture port onto the area schemas and `greem-bench` with its first three workloads: designed in ticket 13, executed after the skeleton runs.
- The wire-level `onError` request attribute: its *design* is on the map; its implementation is not. The three `ErrorBehavior` modes themselves are in the skeleton (ticket 09). `@defer`/`@stream` implementation was moved into scope on 2026-09-26 (ticket 10).
- `#[derive(greem::Abstract)]`: designed in ticket 15, implemented after the skeleton; `greem-macros` ships a stub that points at `Either`/`As`.
