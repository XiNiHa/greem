# How is the BFS executor shown spec-correct?

Type: grilling
Status: resolved
Assignee: Iha Shin
Blocked by: 08, 10, 11
Map: ../map.md

## Question

Design the reference depth-first executor (per object: walk the selection set, dispatch on field name to the field's `Resolver`, answer `__typename` inline, recurse into the child type's completion, insert under the response key), the property-based BFS≡DFS equivalence tests (document and data generators, what 'equivalent' means for error ordering), the hand-written spec-algorithm tests, and a first benchmark baseline on the article's list-repetition workload.

From ticket 08: both executors should produce the same `Value<'req>`-based response through the same `Response: Serialize` view, so equivalence compares arena contents (or serialized JSON) plus the error list with lazily built paths; error ordering may differ between BFS and DFS — define "equivalent" over sets of (path, message).

From [Does the Outputs<Ty> trait encoding survive breadth-first execution?](07-outputs-encoding-prototype.md): compare serialized responses within their retained-owner callbacks or compare owned serialized outputs; no frame-dependent response may escape. Cover split same-type abstract arms, object errors before any selected child field, cardinality failures, cancellation with borrowed destructors, and the policy from [What execution-depth limits bound retained generation frames?](17-generation-depth-limits.md).

From [How does post-hoc null propagation and onError work over the arena?](09-nullability-and-onerror-semantics.md): the "cannot return null for non-nullable field" spec test class is vacuous in greem (compile error); cover instead: error-driven propagation through nested list levels of mixed nullability, `Propagated` vs `Null` slots, deterministic `errors` order (per scope, generation order), all three `ErrorBehavior` modes including HALT's single-error `data: null` response, mutation early termination per mode, and per-object cardinality errors. Equivalence over sets of (path, message) still applies to the DFS oracle, which has no generation order.

From [How do @defer and @stream map onto generations and the arena?](10-incremental-delivery-in-generations.md): equivalence for an incremental stream is two-layered. Property: whenever the `Disabled` execution raises no error that propagates across a defer or stream boundary, folding the incremental stream (apply each incremental entry at `path` + `subPath`, append items in order) equals the `Disabled` BFS result, itself ≡ DFS, with errors compared as sets of (path, message); ids are deterministic (per-request counter at release, scope then object order). Failed delivery groups, nulled-parent cancellation at release, non-null stream termination and per-group HALT are hand-written spec tests using graphql-js's `defer-test.ts` / `stream-test.ts` cases as fixtures. The reference executor learns no incremental semantics.

From [What can a field say to its ancestors during planning, and what does the skeleton ship?](11-planning-hooks.md): the reference executor runs the identical planning pass (same tree, same post-order) so both executors see the same hints; hints may shape results, so there is no "defaults only" mode. The fold-and-compare property for incremental delivery is conditional: it holds for documents whose hint writers do not consult their delivery group, since the `Disabled` tree has none. Cover: a hint reaching an ancestor through an interface arm; an accepting field under two different parents (`Query.posts`, `User.posts`); a hint from a deferred subtree applied to the initial payload; a writer with no acceptor above it (no-op).

From [How does SDL become generated code, and how does the runtime get the schema?](12-build-pipeline-and-crate-layout.md): the reference executor is the unpublished workspace crate `greem-reference`, consumed only by the compliance crate; its dispatch and completion traits live hidden in `greem::__private` and greem-build emits their impls only under the hidden `reference_executor(true)` option, so the compliance fixture's `build.rs` sets it. Both executors take the same `Arc<Document>` from `Schema::parse` and the same `Operation`; introspection selections are pre-resolved through apollo in both. Compare `ExecutionOutput` payload bytes or the folded JSON, never frame-borrowed responses. Add the coercion cases greem now owns: `CoerceArgumentValues` with literals, variables and defaults, `Enum` vs string literal rejection, `Int` range checks on every accepted integer type, `Maybe<T>` absent/null/value for an `absent_aware` input type, and a `Codec::Uuid`/`Codec::Json` round trip.

## Answer

Agreed with Iha Shin, 2026-09-28. Sixteen questions over two rounds; all resolved as recommended except one where Iha chose differently: the compliance crate may hold several schemas (Q8), which amends ticket 12's one-file-per-crate rule. Iha also set the benchmark's direction: it must evolve into performance comparisons against existing frameworks across languages (Q11), which shaped Q15 and Q16.

1. **Reference executor.** `greem-reference` walks depth-first and builds a `serde_json::Value` (`data` plus `errors`) directly while recursing, with null propagation done the spec's way by returning the error up the recursion: no arena, no shape descriptors, nothing shared with the machinery under test except the execution tree, the planning pass (ticket 11) and apollo's introspection slice. It calls the same `Resolver` impls with a one-element parent slice per object and drains a `Streamed<S>` in place through `ReferenceComplete`. It takes `ErrorBehavior` so every mode has a spec-like oracle.
2. **Equivalent means.** `data`: ordered JSON equality, the BFS `ExecutionOutput` bytes parsed with `serde_json`'s `preserve_order` against the reference value. `errors`: multiset of full error objects (`message`, `path`, `locations`, `extensions`), order ignored. Both executors share the tree and its spans, so `locations` and `extensions.code` must agree.
3. **Property inputs.** One fixed property schema, richer than the axum example (nested lists of mixed nullability, an interface with a sub-interface, a union, arguments with defaults, an `absent_aware` input, a custom scalar, mutations, a streamed list). Three generated inputs under `proptest`, each shrinkable: the document (schema-aware strategy: valid selections, fragments, aliases, `@skip`/`@include` variables, `@defer`/`@stream` placements); the world (a seeded in-memory dataset on the app context fixing object counts, the abstract arm per item, an error-injection map keyed by type, field and object id, and a cardinality-failure flag); and the interleaving (a yield count per resolver call, run under a single-threaded `futures::executor::block_on`, so join-order bugs reproduce and shrink). Compliance resolvers are pure functions of the world. No tokio in the crate.
4. **Mode coverage.** `Null` and `Propagate` compare fully. `Halt` checks the weaker property: `data: null`, exactly one error, and that error is a member of BFS's own `Null`-mode error multiset; which error comes first is a hand-written BFS test.
5. **Incremental fold.** Fold the `Enabled` payload stream (apply each incremental entry at `path` + `subPath`, append items in order) and compare with the `Disabled` BFS result, itself compared with the reference. Precondition by `prop_assume!` whenever any `completed` entry carries errors; track the discard rate. The property schema's hint writers never read their delivery group, so the fold property is unconditional in the harness; the group-reading writer is a hand-written test.
6. **Breadth-first claim.** A property over the call log on the app context: BFS invokes each field's resolver once per non-empty scope per generation and the reference once per object, so the BFS count never grows with object count.
7. **Determinism.** Two properties: the same document, world and interleaving give byte-identical BFS output twice; varying only the interleaving gives identical output. These prove ticket 09's `errors` order and ticket 10's ids.
8. **Hand-written spec tests.** graphql-js cases (`executor`, `nonnull`, `lists`, `abstract`, `union-interface`, `variables`, `defer`, `stream`) ported onto one **area schema** per spec area, capped there: extend the area schema before adding another. Grouped by spec section number; each test is query, variables, world configuration, `ExecuteOptions`, expected JSON. Expected outputs are plain checked-in JSON compared by assertion, written by hand from the spec and reviewed, never accepted from a snapshot tool. The "cannot return null for non-nullable field" class stays vacuous (ticket 09). The coercion cases from ticket 12 live here too, since they need generated `Args` structs.
9. **Several schemas per crate.** Amends ticket 12: `configure().file_name("lists.rs")` writes `OUT_DIR/lists.rs` and `greem::include_schema!("lists.rs")` includes it; the argument-less forms keep the defaults. Each `configure()` carries its own `scalar`, `absent_aware` and `reference_executor` settings; `#[greem::object(schema = crate::lists)]` selects the module.
10. **Cancellation.** A gate resolver in the world stays pending until told; the test drops the execution future and asserts child-before-parent destruction through a drop log on the context. Hand-written for mid-generation, mid-stream-turn and during-release; plus one property that drops after a seeded number of polls and asserts no panic and a well-ordered log. Depth-limit cases follow ticket 17.
11. **Benchmarks.** An unpublished `greem-bench` crate owns a `workloads/` directory and every consumer of it. A workload is portable and not Rust: SDL, document, a deterministic dataset description (seed, sizes, an optional fixed simulated latency per resolver call) and a prose resolver contract (pure functions of the dataset). First three workloads: a flat list of many leaves; a nested list with the per-object sugar; an abstract list with partition. The `criterion` consumer measures greem BFS against `greem-reference` in one process, to serialized bytes, reporting wall time and resolver call count; allocations later. A future harness re-implements the same contracts in async-graphql, graphql-js and others and measures over HTTP.
12. **Crate and CI.** `greem-compliance`, `publish = false`, its own `build.rs` with `reference_executor(true)` per schema, proptest regression files committed, CI at the default case count and a nightly job with a larger one.

### Scope

The skeleton (14) ships `greem-compliance` with `greem-reference`, the property schema, the equivalence, call-count and determinism properties, the fold property, and a small hand-written set including the cancellation shapes. The full graphql-js port onto area schemas and `greem-bench` with its first three workloads are execution after the map ends, recorded on the map as named follow-ups. Build pipeline (12): the `file_name` amendment. Depth limits (17): its stress evidence lands as compliance tests using the gate resolver and drop log.
