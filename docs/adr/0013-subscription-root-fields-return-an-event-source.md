# A subscription root field is an ordinary resolver that returns an event source

graphql-js, and every framework that copies it, splits a subscription root field into `subscribe` (called once, returns the source stream) and `resolve` (called per event with the event as the root value). greem collapses the two: the subscription root field is an ordinary `Resolver` impl on the subscription root value whose output is any `Stream<Item = Result<T, Error>>` with `T: Outputs<Ty>`, typed by a generated `EventSource<Ty>` tag beside `List` and `Nullable`, so only a stream type-checks at a subscription root field and the schema-boundary rule holds unchanged. Each item is the field's value for one event; the item's selections run as ordinary generations in a chain of their own and ship as one complete response. Mapping an event to a value is the user's `map` on the stream. The field's arguments, request context and hints are in hand when the event source is created, so a resolver can shape per-event fetches up front.

## Considered options

- The graphql-js split: a `Subscribe<F>` trait with an associated `Event: Resolver<F>` executed as the root object of each event. It keeps the per-event step set-based, which would let a batch of events share one root-field call, and it matches the ported `subscribe` suite as first written. It costs a second trait and a second Rust type, and either one event type for every subscription field (each resolver answering `None` for the others' events, since the generated object completion is bounded on every field) or a second, field-specific root completion path in executor and codegen. Hints would reach the per-event resolver, not the subscribe step, where they are useful.
- Per-event execution with the event as root value but no new trait, graphql-js's default identity `resolve`: the same wart about one event type for every field, and nothing left for the resolver to do.

## Consequences

The set-based root mapping over a batch of events is given up; a user who wants it batches inside the stream, and greem batches everything beneath the root field anyway, so opportunistic event batching stays possible later without touching the contract. A resolver `Err` is one error response then completion; an `Err` item is an error response at the root field path and the stream continues, since a Rust stream does not end on `Err`; an event's execution error, under any error behavior, belongs to that event's response. `@defer` and `@stream` follow graphql-js: a literal use is a request error, a variable `if` that resolves true is a per-event execution error at the enclosing field. The response stream is the same pulled `execute_stream` as every operation, with one complete payload per event, no buffering and cancellation by drop; transports frame it outside the core.
