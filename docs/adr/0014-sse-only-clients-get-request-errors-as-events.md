# An SSE-only client gets request errors as events, not status codes

`greem::http::handle` serves graphql-sse's distinct connections mode as a third framing beside a single JSON body and `multipart/mixed`: one `next` event per payload, `complete` after the last. For a client whose `Accept` names `text/event-stream` and no JSON type, every response is an event stream at 200, request errors included: a document that does not parse or validate is a `next` event carrying `errors`, then `complete`. That contradicts ADR-0012, which answers request errors with 400 or 422 under every media type, and it is deliberate: graphql-sse's protocol requires it, because a browser `EventSource` that receives a 4xx fails the connection with an error event that carries nothing, so the client never learns what was wrong. A client that also accepts a JSON type keeps the draft's status codes, and only a response that streams (a subscription, or `@defer`/`@stream` when SSE is the chosen framing) goes out as events. HTTP-level rejections (405, 406, 415) stay plain status codes for every client; the protocol's "validation steps" are GraphQL's, not the method or body checks.

## Considered options

- The draft everywhere, as ADR-0012 does for `multipart/mixed`-only clients: a graphql-sse client would get a 422 it cannot read, and the protocol's own server answers validation errors as events.
- Events for every client that accepts `text/event-stream`, preferred or not: a client that lists JSON first would get its errors in a framing it did not prefer, and the multipart rule already says a single result goes out as the single type when one is accepted.

## Consequences

Negotiation gains `text/event-stream` as a single media type (SSE-only, like `Media::Multipart`) and as a streaming framing. A subscription streams whenever the client accepts `text/event-stream` at all, since nothing else can carry it, and gets 406 otherwise; incremental delivery over SSE follows the multipart rule (preferred at least as much as the single type), and when both qualify multipart wins a full tie, as the framing the incremental RFC defines. "SSE-only" means `text/event-stream` was chosen as the single media type: a client that reads both streaming framings and no JSON is a multipart client by that tie, and its request errors are status codes as ADR-0012 has them. The `complete` event carries an empty `data:` line, which `EventSource` needs to fire it, and is chained on by `handle` after the payload stream ends, since the payload encoder never sees the end. Single connection mode (reservation tokens, one multiplexed stream, `DELETE` to stop) is not served: it needs a reservation table and expiry timers, which the core does not have (ADR-0008); if ever wanted it is a sibling of graphql-ws's protocol state machine, not a change to `handle`.
